## Conclusions

- On this GSI, `ro.debuggable=1` is not required for the Lineage/crDroid
  rooted-debugging path. The supported `adbroot_service`, enabled by the
  system Settings UI, successfully restarts adbd as root.
- The early `init_boot` ramdisk property file is not the source of
  `ro.debuggable=0`; it contains no such property.
- A `/force_debuggable` ramdisk experiment would be invalid on the current
  locked/green boot unless its verified-boot gate were also addressed.
- The runtime privilege prerequisite for a GSI SPI trace is satisfied.
- The GSI trace directly confirms multiple framebuffer submissions per visual
  update, different geometries/content sources, and frame-transfer count
  tracking submission count after separating window-command work.
- The remaining pre-patch gate is a controlled real full-screen client target
  that demonstrates how the plane/transfer count and physical output change.

## Disproven assumptions

- “The next root experiment must patch `ro.debuggable` in `init_boot`” is
  false for this GSI. The inspected ramdisk does not carry the property, and
  the GSI already provides a supported rooted-debugging control.

root control. The correction is to inspect the candidate source and exhaust
